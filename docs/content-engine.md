# Offline content engine authoring foundation (v1)

This foundation prepares **original practice**, not real, recalled, scraped, or ripped certification exams. The approved planning goal is **1,000 accepted exercises in each of six modes for each of 38 courses**, excluding 309: 228 course/mode cells, 228,000 total. It does not generate that content, call models, access a database, load production environment files, activate releases, or deploy. Existing learner content is unchanged.

The baseline input is the immutable `server/interactiveContent/release-2026-11-12` release: 38 packs containing 3,821 exercises. The reader pins the release metadata SHA-256 and checks each existing package/provenance file against its recorded byte hash. Missing packages produce zero cells, never inferred coverage; changed or unexpected packages fail closed. Input files are read only. No runtime loader/router/client import is needed.

## Files and contracts

All implementation is under `scripts/content-engine/`. `constants.mjs` fixes scope and target. `schemas.mjs` exports strict Zod `SourceSchema`, `ConceptSchema`, `ExerciseSchema`, `ReviewSchema`, `DocumentSchema`, `CalculationSchema`, `PayloadSchema`, `ReviewPolicySchema`, and `BatchAuditSchema`. `identity.mjs`, `coverage.mjs`, `review-policy.mjs`, `calculations.mjs`, and `planner.mjs` are pure. `inventory.mjs` reads only when called; `storage.mjs` writes only through explicit methods. `cli.mjs` runs only as its entry point. `fixtures.mjs` contains synthetic software-test evidence, not real review, batch audit, calibration, independence, or rights authorization.

Every authoring document/source/concept/exercise/review uses `schemaVersion: "content-engine-v1"`. Calculation checks use `calculation-v1`. Optional batch audits use `batch-audit-v1`, with `policyVersion: "risk-based-carbon-v1"`. Unknown versions and extra fields are rejected rather than silently migrated. Old documents remain valid and conservative; no existing records gain approval through migration.

**Source** records contain `sourceId`, `publisher`, `title`, `url`, `docLocator`, `retrievedAt`, `snapshotHash`, `rightsBasis`, `permittedUsage`, and located evidence with `evidenceId`, `excerpt`, and `snapshotHash`. Unknown legacy values are null/empty. A public URL is neither permission nor retrieved evidence. Complete records require documented rights, `original-practice-derivation` permitted usage, located snapshot-bound evidence, and retrieval time. The code checks declarations/completeness, not license validity or source authenticity.

**Concept** records contain located facts with source evidence references, concept-level references, applicability objects `{courseKey, jurisdiction, examLevel, blueprintVersion, objectiveId}`, and variant families with learning intent and parameter definitions. References must resolve uniquely; the exercise must match a concept's declared applicability and variant family. No course-name parsing fabricates objectives or blueprint mappings.

**Exercise** envelopes preserve `item` exactly in its existing renderer payload shape and include `exerciseId`, `courseKey`, `mode`, `conceptRefs`, `objectiveId`, `jurisdiction`, `examLevel`, `blueprintVersion`, `difficulty`, `difficultyRationale`, `variantFamilyId`, `parameters`, `units`, `sourceEvidenceRefs`, `contentHash`, `claimType`, `originality`, `authorityEvidence`, `calculationChecks`, `reviews`, and optional historical `legacy` metadata. Difficulty is `easy | medium | hard | unclassified`; historical exercises stay unclassified. Do not infer difficulty, objectives, source rights, originality, or human approval from release status.

The six per-mode checks cover Boolean swipe answers, 3–20 matching pairs, 2–20 keyed options for odd-one-out/cause-effect/tap-the-flaw, and either before/after answers or two uniquely matching before/after labels. Matching/option IDs and visible labels must be unique; before/after hints and exposed labels are conservatively blocked. These are structural heuristics, not instructional or scientific approval. The mirrored pure payload shape matches the newly exported `shared/interactiveSessions.ts` `interactiveDrillExampleSchema`; a guarded compatibility test compares all six modes and malformed inputs. `payloadIssues(item, interactiveDrillExampleSchema)` can inject only that pure schema when needed. No loader/registry/live backend import or production file change was needed. The checked compiler described below validates the actual server package constraints; the authoring target does not change the 300-item legacy compatibility limit.

## Reviews and release gate

Review records contain `kind`, `status`, `reviewer`, `reviewerAuthority`, `authorityEvidence`, `reviewedAt`, `payloadHash`, `subjectHash`, and explicit documentary `evidence` entries `{locator, sha256, summary}`. The authority labels are deliberately `ai-model-declared`, `human-technical-declared`, `software-release-declared`, and `human-diversity-declared`. A signature/name/declared role is **not independently verified identity or authority**. Non-AI reviews require documentary authority evidence, but this software does not authenticate it. An approval string, an AI `humanApproved` field, or an unsigned blanket assertion is insufficient.

`contentHash` hashes the exact payload. `subjectHash(exercise, document)` binds all exercise metadata and payload (excluding the review list), the referenced concept facts/applicability/families, and all referenced sources including authority sources. Editing an answer, explanation, citation, source excerpt, rights basis, difficulty/rationale, objective, parameters, or authority evidence invalidates existing approvals even if the payload hash is recalculated. Evidence must have explicit locators and hash declarations. All reviews of a given kind must be approved and current; a stale/rejected/conflicting review cannot be hidden by a later row. Review documents must be checked independently by authorized people before real release decisions.

AI review and software release are separate from human technical approval. The default policy (`conservative-per-item-v1`) requires complete metadata, passing structural/calculation checks, current documentary human-technical and software-release reviews, and no unresolved duplicate/conflict/variant-family flags for `releasableAccepted`. AI review is optional under this default and never substitutes for its human gate. This metric is **candidate eligibility under declared evidence, not production activation or independent factual verification**.

Statutory/safety records need located jurisdiction-specific authority evidence. The existing pure `scripts/echelonsix-legal-screen.mjs` screen is also applied by the offline blockers and remains fail closed, including its manual exclusions. This foundation does not override or relax the existing screen even for a supplied human review. The existing release workflow remains mandatory; the checked export described below does not activate or deploy content.

### Optional risk-based Carbon review policy (v1)

The minimal opt-in hook is an authoring-document field `reviewPolicy: { policyVersion: "risk-based-carbon-v1", enabled: true }`, plus explicitly supplied `batchAudits`. The existing `report` and `validate` commands use these fields without new commands, network calls, AI generation, credentials, database state, or activation. There is no default opt-in, executable hook, automatic audit record creation, or permission to assert a real batch audit occurred. **Without a supplied current approved batch audit, the alternative path is blocked.** The policy name records the approved Carbon plan, not a claim that Carbon exists or was called.

Only `claimType: "concept"`, `originality: "original-practice"`, non-legacy content can use the alternative path. Every item must have independent-AI evidence declaring `riskScope: "routine-non-operational-concept"`. Items with an `instruction` field or conservative operating/procedure/safety/duty language remain ineligible. `field-practice`, safety, statutory, and unclassified items cannot use batch authorization instead of the existing per-item declared qualified-human authority gate. This intentionally narrow classifier is a fail-closed precaution, not a semantic safety detector. The legal screen runs unchanged regardless of review route. A rejected or stale per-item human decision cannot be hidden by the policy.

Each routine item needs an approved current hash-bound `ai` review and an approved current `software-release` review, both explicitly recording `policyVersion: "risk-based-carbon-v1"`. The AI review must also supply `independentAI` with a distinct declared `generatorIdentity`, located `independenceEvidence`, `correctnessEvidence`, `sourceCheckEvidence`, `blueprintAlignmentEvidence`, and `duplicateCheckEvidence`. Evidence objects use `{locator, sha256, summary}`. A distinct model/reviewer name alone is not proof of independent review; the module requires evidence declarations but does not verify them or call a model. Source snapshot/rights resolution, concept facts, exact blueprint/objective/applicability alignment, calculation checks, duplicate/conflict quarantine, and variant-family parameter/diversity gates all continue to apply. Software release alone or AI alone is not approval.

A `batch-audit-v1` record must declare the policy version, unique `batchId`, approved status, a declared human technical auditor with non-null authority evidence, `reviewedAt`, and the truthful scope `sampled-batch-not-per-item`. Its bounded `members` list (1–12) records `{courseKey, exerciseId, payloadHash, subjectHash, reviewBindingsHash}` from the pure `auditBinding(exercise, document)` helper. `sampledMembers` must be a nonempty distinct subset of those members: an unsampled item may receive batch authorization, never a human-review flag. Supply the actual `samplingMethod`, `calibrationEvidence`, `findingsEvidence`, `sourceCheckEvidence`, `blueprintAlignmentEvidence`, and `duplicateCheckEvidence`, with an empty `unresolvedFindings` list. Calibration evidence must truthfully document the sample design and why the observed findings support authorizing this bounded batch; a blank, invented, or unperformed audit is not authorization. Software checks declarations and membership only, not statistical adequacy, identity, credentials, findings truth, or document authenticity. Authorized reviewers must assess the actual evidence before any real release.

Set `corpusHash` using `auditCorpusHash(document)` after item reviews are recorded. The batch binds the exact item-review records and full corpus source/metadata hashes, so edits to answers, explanations, source text/rights, blueprint metadata, independent-review evidence, or software decisions invalidate the audit. Adding/removing corpus items also invalidates the audit, including changes to duplicate context. Every supplied audit touching a member must be current and approved; rejected/stale/conflicting audits cannot be shadowed by another row. Regeneration of a hash is not itself a new audit. New authorization requires a genuinely performed review and explicitly supplied documentary decision.

Reports and validation record `reviewPolicyVersion`. `riskPolicyAccepted` counts accepted candidates using the alternative route, separately from `humanReviewed`. Batch authorization **never increments `humanReviewed`, never claims every item was human reviewed, and never claims declared identities, independence, calibration, or authority were verified**. All supplied records in fixture helpers are synthetic software-test data only. No real batch audits are provided by this implementation; existing 3,821 legacy items remain unaccepted, and learner content is unchanged.

## Inventory and coverage honesty

`inventory` reads the 3,821 released payloads into transient unreviewed envelopes; `stage` optionally persists them privately. Provenance URLs become unresolved source records. Historical AI declarations and `approved` software release status are retained separately; neither becomes a hash-bound current review. The immutable packs/provenance remain the original evidence and are not rewritten.

Every report includes all 228 rows with `target: 1000`, `raw`, `unique`, `duplicate`, `conflict`, `quarantined`, `nearDuplicateFlagged`, `metadataComplete`, `AIreviewed`, `humanReviewed`, `riskPolicyAccepted`, `releasableAccepted`, and `remainingGap`, plus `legacyInventory`, `legacyAIReviewDeclared`, `legacySoftwareReleased`, and `unclassifiedDifficulty`. `remainingGap = max(0, 1000 - releasableAccepted)`, not 1000 minus raw legacy records. `humanReviewed` still means a current declared per-item human-technical review, never a sampled batch audit.

`unique` counts distinct exact scientific problem+answer fingerprints; `duplicate` is raw minus that count. Those descriptive counts do not imply accepted coverage. Identical problem groups are entirely quarantined; contradictory keyed answers or difficulty classifications quarantine every member, not whichever duplicate was read last. Duplicate storage IDs also quarantine all affected groups. `metadataComplete`, `AIreviewed`, and `humanReviewed` count only singleton, non-quarantined exercise candidates. This intentionally conservative policy requires explicit consolidation outside the inventory, never silent overwrite.

Fingerprints use NFC and whitespace normalization only: **2² differs from 22; ML differs from mL**. Numbers, equations, subscripts/superscripts, symbols, unit case, and science-bearing instructions survive. Keyed answers are canonicalized by their label; storage IDs, option/pair presentation ordering and explanation rewording cannot manufacture coverage. Renderer-only hazard checks retain their conservative label folding, separately from scientific identity.

Different wording is not proof of a different learning task. Declared variant-family siblings with different problem hashes are flagged; identical parameter signatures remain quarantined even with a diversity review. Distinct parameter signatures require an explicit current `coverage-diversity` review to resolve the flag, plus all other acceptance gates. This does not solve semantic similarity or embeddings. Undeclared legacy families remain unknown and unaccepted; later authoring/review must detect and map reworded equivalents rather than treating raw fingerprint uniqueness as legitimate breadth.

## Private output and persistence

The CLI permits **only relative filenames under `/home/ubuntu/outputs/echelon-content-engine`**. It denies all repository output, including every `client`, `shared`, `public`, and `dist/public` destination. The root is fixed, not an environment variable or CLI override. Absolute paths, dot/traversal segments, root/directory/file symlinks, and canonical realpath escapes are rejected. The library's root injection exists for disposable tests, not a production authorization to redirect CLI output.

Files are written to exclusive 0600 temporary files, fsynced, and published atomically. New outputs refuse overwrite using an atomic no-clobber hard-link publication. The small bounded pilot JSONL ledger uses explicit atomic replacement instead of partial appends; a truncated ledger refuses resumption. Directory creation uses 0700; pre-existing parent permissions remain the operator's responsibility. Use a private operator-controlled parent directory and one writer. These filesystem checks are defense in depth, not protection against a malicious local process racing directory changes or concurrent ledger writers. No new database is used.

## Bounded future pilot planning (no generation)

`plan-default` writes a six-item, two-item-batch, USD 1, one-retry configuration with `pilotOnly: true` and `dryRun: true`. Hard limits are 12 items, 4 items/batch, USD 5, 2 retries, 20,000 input tokens and 12,000 output tokens/batch. Configuration cannot contain credentials, alternative providers, executable hooks, or a dry-run override.

The plan requires a supplied snapshot of the **current direct Google** model catalog (`https://generativelanguage.googleapis.com/v1beta/models`), less than 24 hours old at the explicitly supplied `NOW_ISO`, with `provider`, `endpoint`, `retrievedAt`, the untouched JSON `response`, and `responseHash: hash(response)`. `Carbon` is a selector, not a hardcoded current model ID. `selectCarbon` requires exactly one matching generation-capable model; absent/ambiguous Carbon blocks planning. No assertion that Carbon currently exists is made; no catalog call was made in this task. A later authorized main orchestrator must obtain the actual current catalog and manage credentials securely.

The Google models catalog does not establish prices. A separate pricing document must declare `modelName`, `inputUSDPerMillion`, `outputUSDPerMillion` and documentary `evidence`. The planner reserves the worst configured input/output spend per attempt in integer micro-USD, tracks every reserved attempt (including failed attempts), enforces retry/spend caps, skips completed batches, and refuses an unresolved reservation. Changed model/catalog/pricing bindings require a new ledger. No cost refunds are inferred from failures. A later runner must enforce the configured token ceilings and stop before any request that could exceed the reserved limits.

The planner returns a **proposed** reservation only. It never writes it and never makes a request. Before a later authorized call, the orchestrator must durably write the reservation via `appendLedger`, then append a matching `completed` or `failed` event. On a crash with an open reservation, do not automatically retry: reconcile explicit documentary request evidence first. Ledger records use `schemaVersion`, `configHash`, `executionHash`, `batchId`, `attempt`, `status`, and `reservedSpendMicros`. A transport, credential handling, request execution, source acquisition, and pilot generation are intentionally not implemented here.

An operator computing a hash of whatever they supplied does not establish completeness. ### Private runtime artifact identity

The public `release`/`releaseKind` marker still identifies source only: identical source can produce different private runtime content. A successful server build also creates `dist/interactive-content-build-manifest.json` (0600) outside `dist/public`, alongside `dist/interactive-content`. It contains `version: 1`, `kind: "interactive-artifact-sha256-v1"`, and one SHA-256. This is answer-derived sensitive metadata: keep it and any copied expected digest private, never publish it, put it in logs, or expose it through health, a client bundle, or a static file server. SHA-256 is not encryption; stable hashes can enable guessing or correlation. Restrict build artifact storage and parent-directory access as well as the file itself. No new endpoint or privilege is provided.

The fingerprint covers every regular file in the final copied runtime tree, including registry, metadata, manifests, legacy packages and shards. Symlinks and missing registry fail the build. It is SHA-256 of UTF-8 `echelon-interactive-artifact-sha256-v1` and NUL, followed by files in bytewise UTF-8 POSIX relative path order, each framed by an unsigned 64-bit big-endian byte length, path bytes, unsigned 64-bit big-endian content length and exact content bytes. Empty directories, permissions, timestamps, source documents, server bundle, dependencies and external/database state are not included. Copying the manifest alone does not verify the deployed bytes. Filesystem protection assumes a private operator-controlled tree and no concurrent writers; it is not a defense against a malicious local process racing the build or check.

For a future separately authorized release, have an authorized operator retain the expected manifest from the exact reviewed build through a trusted private channel, independently verify the existing public source marker, and compare the full kind and SHA-256 to the manifest from **each deployed instance**. The operator must also recompute `computeInteractiveArtifactFingerprint` from that instance's actual `dist/interactive-content` and compare it to the retained expected SHA-256, using private local/operator tooling without emitting the digest to public output or logs. Ensure the inspected directory is the one used by the running instance; repeat after any replacement or mutation. If private access or per-instance verification is unavailable, exact content deployment is unverified. An untrusted manifest is not a signature, approval, proof of runtime behavior, or protection against a compromised operator/host. Owner approval and all existing review/deployment gates remain separate; the trusted corpus allowlist is still empty, so checked builds remain fail closed.

For example, from a trusted checkout of the same verifier code, with local read access to one instance's mounted `dist` and the separately retained expected manifest, run the following with private paths substituted (do not copy the actual hashes into shell history):

```sh
EXPECTED_MANIFEST=/private/reviewed-build-manifest.json INSTANCE_DIST=/private/instance/dist node --import tsx --input-type=module <<'NODE'
import { readFileSync } from "node:fs";
import { join } from "node:path";
import { computeInteractiveArtifactFingerprint } from "./scripts/interactiveArtifactFingerprint.ts";
try {
  const expected = JSON.parse(readFileSync(process.env.EXPECTED_MANIFEST, "utf8"));
  const actual = JSON.parse(readFileSync(join(process.env.INSTANCE_DIST, "interactive-content-build-manifest.json"), "utf8"));
  const valid = m => m && m.version === 1 && m.kind === "interactive-artifact-sha256-v1" && /^[a-f0-9]{64}$/.test(m.sha256);
  if (!valid(expected) || !valid(actual) || expected.sha256 !== actual.sha256 ||
      expected.sha256 !== computeInteractiveArtifactFingerprint(join(process.env.INSTANCE_DIST, "interactive-content"))) throw Error();
  console.log("Private artifact verification passed");
} catch {
  console.error("Private artifact verification failed");
  process.exitCode = 1;
}
NODE
```
