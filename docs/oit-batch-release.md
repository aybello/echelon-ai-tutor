This uses a read-only transaction and reports matching visible/staged counts, missing or conflicting rows, rejected items, duplicate numbers and exact normalized duplicate stems across the complete existing banks. Retain this output. Public inventory counts alone cannot establish whether this package is live.

If an older package was already staged, its earlier choices will correctly register as content conflicts: neither repeated import nor activation updates them. Retain a read-only row-level comparison and use a separately reviewed, backup-confirmed exact-version content update before proceeding. Never bypass the conflict check. The exact-stem comparison does not establish semantic originality against the legacy bank; review any known source-overlap concerns before release.
4. Verify a recoverable database backup and retain the pre-release report and commit SHA. After checks pass, run `CONFIRM_OIT_RELEASE=<full-printed-sha256> node scripts/release-oit-question-banks.mjs --apply`. This locks the bank metadata and question rows, repeats all comparisons, publishes only matching staged package rows, checks exact visible totals, and commits both banks together. A failure rolls back the batch. Already-visible matching rows remain unchanged; repeat execution does not bump versions again.
