# Test safety boundary

The November 11 incident showed that even nominal unit tests may use inherited production settings. Start Vitest and both checked-in Playwright configurations with `scripts/test-safety.cjs` as the **first Node startup preload**, before the runner and any other preload or application import. The checked-in package scripts and CI runner commands do this; an unpreloaded runner is rejected by its config. For example:

```sh
env -i PATH="$PATH" HOME=/tmp node --require ./scripts/test-safety.cjs ./node_modules/vitest/vitest.mjs run server/jobPdfText.test.ts --maxWorkers 1 --minWorkers 1
env -i PATH="$PATH" HOME=/tmp node --require ./scripts/test-safety.cjs ./node_modules/@playwright/test/cli.js test --list
```

Existing standalone Node test files import the guard first; for new standalone tests and runners, prefer `node --require ./scripts/test-safety.cjs --test …`. If mysql2 or dotenv was already loaded before installation, the guard rejects startup rather than trusting already-captured references. This detection relies on Node's CommonJS cache and is not a guarantee against custom loaders, alternate copies not represented there, native code, or deliberately modified caches. New runners and custom configs must enforce their own startup preload. Do not supply production credentials, URLs, or an inherited `NODE_OPTIONS`.

The guard rejects nonempty database URLs unless the exact opt-in is present and the URL is mysql on literal `127.0.0.1:3306` with an approved schema; it rejects query strings, cutover selectors and external certificates. The permitted schema names are `echelon_ci`, `echelon_upgrade_ci`, `echelon_standalone_ci`, and the exact `exam_dates_test_` plus 32 lowercase hexadecimal characters generated by the reconciliation integration test. `ECHELON_TEST_DATABASE=I_UNDERSTAND_THIS_IS_A_DISPOSABLE_LOCAL_DATABASE` is required for mysql2 connections, including URLs not present at startup. The selected mysql2 configuration is checked immediately before a socket is opened for supported raw/promise/pool clients. MySQL custom streams, sockets and changeUser are denied. Guarded Node subprocesses inherit the guard even with a replacement environment. Ordinary Node TCP sockets are limited to loopback, and direct connections to port 3306 are denied except during an approved mysql2 connection. Common inherited credentials and live cutover probe endpoints are rejected; diagnostics never print their values. Playwright will not reuse an existing app server or accept a remote `E2E_BASE_URL`.

`DOTENV_CONFIG_PATH=/dev/null` applies to `dotenv/config`, **not** direct `dotenv.config()` or `configDotenv()` calls. The guard additionally replaces those dotenv methods with no-file-read behavior and rejects explicit non-null paths, including ESM imports of the supported package. This only covers the intercepted dotenv package/API: Vite, Node's `--env-file`, other dotenv implementations, manual file reads, previously captured functions, custom loaders and code deliberately changing the hooks can still load secrets. Never rely on this hook instead of removing secrets and `.env` files from the isolated test environment.

**This is defense in depth, not an OS security sandbox or proof of server identity.** Loopback may be a forwarded production server; an approved schema name could exist on a non-disposable local server. Before opting in, independently provision an isolated MySQL server with no production connectivity, dedicated disposable credentials, and the approved database names; never use a tunnel or shared local instance. The guard cannot inspect SQL for cross-schema operations or prove that no triggers, stored procedures, or privileges affect other schemas. Use least privilege and a disposable server, not merely a test-named schema.

The guard cannot comprehensively control non-Node executables, browser networking, native addons, UDP, alternate client protocols or drivers on other loopback ports, custom runner configs, dynamically loaded secrets, a subprocess that deliberately strips Node options after launch, or hostile test code. In particular, loopback HTTP may be forwarded to an external service and browsers can make requests outside Node's socket guard. Use an OS/container-level network and credential boundary (including browser/child processes) for a strong guarantee; do not run unreviewed or broad tests on a production-connected host. The current guard deliberately rejects the optional `PRACTICE_TEST_MYSQL_SOCKET` integration mode; migrate it to a separately sandboxed server before running it. CI, browser, and database-backed jobs require independent validation in such an isolated environment. No real database connection is made by the safety regression tests.
